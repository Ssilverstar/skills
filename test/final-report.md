## 커스텀 Herdr 스킬

새 원본은 [herdr-orchestrate/SKILL.md](../skills/herdr-orchestrate/SKILL.md)입니다. 기존 설치된 `herdr` 스킬은 명령의 기준으로 유지하며 수정하지 않았습니다. 새 스킬은 공통 36개에 포함해 네 에이전트에 배포했습니다.

- [레이아웃](../skills/herdr-orchestrate/references/layout.md): `Codex | Claude | Agents`, 작업자는 오른쪽 세로 분할, 사용자 포커스 유지, 반환된 패널 ID 사용.
- [작업 계약](../skills/herdr-orchestrate/references/contracts.md): 소유 파일·입력·검증·금지 범위·첫 산출물 확인 시점·실행하지 않은 테스트의 `not_run` 표시.
- 관리자는 한 명으로 유지합니다. Codex는 Claude가 맡은 작업자에게 별도 구현 지시를 내리지 않습니다.
- 승인 화면 전체 읽기와 키 입력을 분리하고, 좁은 요청만 처리합니다. 훅을 끄거나 무제한 권한으로 통과시키지 않습니다.
- 두 번 같은 수정이 실패하면 원인을 다시 좁힙니다. 작은 피드백은 묶고, 작업자 완료 후 소유권을 회수한 짧은 수정은 총괄이 처리합니다.
- 완료 장벽: 최신 과제 ID와 RESULT·산출물 시각/해시를 맞추고 실제 화면의 사고/도구/승인/대기 프롬프트를 확인합니다. 총괄의 감시 작업까지 종료한 후 패널을 닫습니다.
- 설정 파일 갱신과 현재 세션 반영, 등록과 실제 도구 호출, 성공 종료 코드와 실제 성공을 구분합니다.

[Opus의 독립 검토](herdr-orchestrate-review-claude.md)와 [실제 운영 워크플로](../herdr/workflows/claude-workers.md)를 함께 기록했습니다.

## 시험 중 발견·수정한 문제

1. Gemini가 실행하지 않은 smoke를 성공으로 보고한 사례가 있어, 실제 화면/E2E와 원본 결과를 최종 기준으로 삼았습니다.
2. Python 소멸자의 ResourceWarning은 exit 0에도 stderr에 남았습니다. 연결 정리와 stderr 검증을 추가했습니다.
3. 영어 번역 함수 단위 테스트가 통과해도 HTML 고정 문구·ARIA·도움말은 한국어로 남았습니다. 실제 DOM 전체를 영어 모드에서 검사하도록 바꿨습니다.
4. Claude 로컬 ECC 복제본은 비활성 원본과 이름이 같아도 로딩되지 않았습니다. `ecc-common`으로 이름을 분리하고 기존 훅의 단일 로딩을 확인합니다.
5. OpenCode headless의 기본 모델이 미지정이면 클라우드 인증 오류가 발생했습니다. 사용자 지정 로컬 Qwen을 기본으로 기록하고 TUI/CLI 검증 결과를 구분했습니다.
6. 브라우저 MCP는 목록 조회가 성공해도 실제 브라우저 실행은 실패했습니다. Ubuntu AppArmor가 원인이었으며 Chromium 파일 하나에만 user namespace 권한을 주어 샌드박스를 유지한 채 해결했습니다.
7. OTel에서 신원 라벨을 지우기 전에 세션별 누적값을 delta로 변환하지 않으면 서로 다른 세션이 덮어씁니다. 변환 순서와 역전된 송신 시각·counter reset을 실제 수집기 fixture로 검증했습니다.
8. MCP 카드의 `gemini`/`antigravity` ID 혼용으로 가짜 다섯 번째 카드가 표시됐습니다. 실제 계약 ID 네 개로 통일하고 실브라우저 개수 검사를 추가했습니다.
9. 스킬 필터의 번역 라벨을 선택 값으로 쓰면 언어 전환 후 필터가 깨졌습니다. 고정 ID와 번역 표시를 분리하고 닫힌 select의 option도 영어 검사에 포함했습니다. 활성 상태 `null`은 0으로 바꾸지 않고 미확인으로 유지합니다.
10. 표가 정렬돼도 실제 셀 내용은 비어 있을 수 있었습니다. MCP 에이전트 열과 모델 점유율 라벨을 비우던 DOM 헬퍼의 자식 요소 처리를 수정하고 행별 ID와 개수를 검사했습니다.
11. OpenCode 문맥 요약에 등장한 RESULT 예문이 감시기를 잘못 깨웠습니다. 실제 결과 파일·최신 작업 ID·화면·실행 상태를 대조해 완료 오판을 막고 감시 조건을 수정했습니다.
12. 마지막 Prometheus scrape 시각을 마지막 수신 시각으로 보여주던 문제를 수정했습니다. 네이티브 값은 최근 24시간 `increase()` 추정이며 첫 관측/장기 공백/수집기 재시작 때문에 일부가 빠질 수 있음을 표시합니다.

## 운영 주소와 제약

- 같은 공유기: <http://192.168.0.65:8787>, 호스트: <http://127.0.0.1:8787>. 호스트 브라우저의 LAN 주소 접속을 확인했습니다. **Windows 실기기의 종단 간 접속은 사용자 측 확인이 필요하며 완료로 주장하지 않습니다.**
- 수집기·Prometheus는 loopback/컨테이너 내부만 노출합니다. 앱은 지정 LAN 주소에 노출합니다.
- 사용자 systemd 프로브는 로그인 후 동작합니다. linger를 켜지 않았으므로 로그아웃 후 수집 지속을 보장하지 않습니다. 웹 컨테이너와 Herdr 작업자 수명은 별개입니다.
- 공통 스킬은 같은 목적의 선택 목록입니다. Claude 네이티브 docx/pdf 등의 구현·호출 이름은 다를 수 있고, 도구가 없는 호스트의 이미지 생성/인라인 시각화까지 실행 가능하다고 보증하지 않습니다.
- 현재 세션에 이미 로딩된 목록은 새 프로세스와 다를 수 있습니다. 전체 스킬 워크플로·모든 MCP 도구를 전수 실행한 것은 아닙니다.

## 단독 실행과 멀티 패널 비교

[QA 회수 무렵 부분 사용량](results/monitor-run-usage-latest.json)은 시험 시작부터 약 348분 구간이며 요구 추가·승인 대기·한도 대기·수정과 QA를 모두 포함합니다. 마지막 OpenCode QA-003 화면은 22분 6초·17.8 tok/s를 표시했습니다. 문맥 요약과 추가 검증을 포함한 관측으로, 모델 자체 성능이나 단독 실행 대비 속도 차이로 해석하지 않습니다.

[상세 비교 표](monitor-study.md#방식별-비교)는 Astra 단독, Opus 단독, 각 모델의 Herdr 총괄, 이번 Codex 검증+Opus 총괄 구조를 구분합니다. 이번에 관측한 장점은 독립 검증이 오판과 누락을 찾아낸 점이고, 비용은 승인 중계·문맥 전달·작은 수정의 왕복·느린 headless 재시도입니다. 작은 작업은 한 에이전트가 끝내고, 파일 경계를 나눌 수 있는 큰 작업에는 총괄 한 명과 필요한 작업자를 두는 방식이 적합합니다. 단독 기준 실행이 없어 속도·비용 우열이나 절감률은 계산하지 않습니다.
